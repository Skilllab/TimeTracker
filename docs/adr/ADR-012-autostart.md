# ADR-012 — Автозапуск приложения

> **Статус:** принято (этап 12 — `stage-12-autostart.md`).
> **Связанные решения:** ADR-002 (структура решения, Clean Architecture), ADR-003 (composition root и DI), ADR-008 (платформенные сервисы).

---

## Контекст

Приложение должно уметь запускаться вместе с системой — по выбору пользователя. Механизм у каждой операционной системы свой: Windows хранит такие записи в ветке реестра текущего пользователя (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`), Linux использует файл `.desktop` в каталоге автозапуска, macOS — LaunchAgent. Если выбор механизма оставить в коде экрана, привязка к системе распространится по слоям: представление начнет обращаться к реестру напрямую.

Отдельно нужно решить, где хранится признак «автозапуск включен». Напрашивающийся ответ — в настройках приложения — создает второе место хранения того же факта.

Ограничения проекта, влияющие на выбор:

- **правило зависимостей** (ADR-002): `Presentation` не ссылается на `Infrastructure`, реализации портов лежат в `Infrastructure`;
- **домен** о платформе не знает: автозапуск — не предметная область, а поведение приложения в системе;
- **принцип Windows-first** (ADR-008): сначала Windows, остальные системы позже;
- **без YAGNI:** механизм поддерживается ровно настолько, насколько нужно рабочему приложению на Windows.

---

## Решение

**Автозапуск оформляется отдельным решением: исходящий порт `IAutoStartService` объявляется в `TimeTracker.Application`, реализации — в `TimeTracker.Infrastructure`.**

1. **Порт описывает намерение, а не механизм:** включить автозапуск, выключить его и узнать текущее состояние. О реестре и о файлах настройки в порту не сказано.
2. **Источник истины — система.** Признак не дублируется в настройках приложения: состояние читается из той же записи, которую создает и удаляет реализация. Поэтому этап не зависит от сохранения настроек.
3. **Реализация — Windows.** Запись создается в ветке реестра текущего пользователя, поэтому права администратора не нужны.
4. **Экран настроек работает с портом.** Переключатель вызывает операции порта и показывает прочитанное состояние, а не последний выбор пользователя.

Объявление порта:

```csharp
/// <summary>
/// Исходящий порт: запуск приложения вместе с системой.
/// </summary>
public interface IAutoStartService
{
    /// <summary>
    /// Включает автозапуск приложения.
    /// </summary>
    void Enable();

    /// <summary>
    /// Выключает автозапуск приложения.
    /// </summary>
    void Disable();

    /// <summary>
    /// Возвращает признак того, что автозапуск включен.
    /// </summary>
    bool IsEnabled();
}
```

## Последствия

**Положительные:**

- выбор механизма операционной системы остается в одном месте — в реализации порта;
- представление и сценарии о реестре не знают, правило зависимостей сохраняется;
- признак не может разойтись сам с собой: он хранится в одном месте — в системе;
- отдельный этап позволил этапу 11 закрыть сервисы с общим механизмом и не смешивать с ними запись в реестр.

**Отрицательные и ограничения:**

- **состояние принадлежит системе.** Если запись удалить в обход приложения, переключатель покажет выключенное положение — это ожидаемое поведение, а не ошибка;
- **запись хранит путь к исполняемому файлу.** При переносе папки приложения автозапуск нужно включать заново: сам путь не обновляется;
- **реализации для Linux и macOS отсутствуют.** Там автозапуск недоступен, пока не появятся соответствующие реализации за тем же портом;
- **чтение состояния происходит при открытии экрана настроек**, а не при запуске приложения: приложение к реестру на старте не обращается.

---

## Альтернативы

1. **Хранить признак в настройках приложения.** Отклонено: появляется второй источник истины, который может расходиться с системой, а этап начал бы зависеть от сохранения настроек.
2. **Вызывать реестр прямо из кода экрана настроек.** Отклонено: привязка к Windows распространилась бы на проект представления, и правило зависимостей перестало бы защищать слой.
3. **Оставить автозапуск внутри этапа платформенных сервисов.** Отклонено: механизм отличается от трея, горячей клавиши и определения простоя — те обращаются к системе во время работы приложения, а автозапуск однократно меняет запись и дальше в работе не участвует.
