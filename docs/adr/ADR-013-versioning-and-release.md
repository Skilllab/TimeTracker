# ADR-013 — Версионирование и релизная поставка

> **Статус:** принято (этап 19 — `stage-19-packaging-release.md`).
> **Связанные решения:** ADR-002 (структура решения, Clean Architecture), ADR-003 (composition root, порядок инициализации), ADR-008 (платформенные сервисы), ADR-009 (упаковка и обновление).

---

## Контекст

Этап 19 делает приложение **устанавливаемым**: появляются установщик, автообновление и номер версии, который пользователь видит в настройках. До этого этапа номер версии был объявлен одним свойством `Version` в `Directory.Build.props`, а релизный конвейер публиковал папку сборки: установщика не существовало, и вопрос о том, откуда берется номер, не был решен.

Нужно ответить на три вопроса: **где** хранится номер версии, **кто** его меняет и **что именно** получает пользователь.

Ручная правка номера в файле перед релизом создает второе место для того же факта: номер есть и в теге ветки, и в файле сборки. Два места расходятся, и установщик собирается с чужим номером — при этом ошибка обнаруживается только у пользователя.

Ограничения проекта, влияющие на выбор:

- **правило зависимостей** (ADR-002): поставка не меняет устройство слоев, код домена и сценариев о версии не знает;
- **принцип Windows-first** (ADR-008, ADR-009): сначала закрывается Windows, остальные системы позже;
- **данные пользователя неприкосновенны**: БД и настройки лежат в папке данных **вне** области установки (см. `data-model.md`), поэтому замена файлов приложения их не затрагивает;
- **без YAGNI:** берем ровно тот механизм, который нужен рабочему приложению.

---

## Решение

**Единственный источник версии — свойство сборки `VersionPrefix` в `Directory.Build.props`; значение записывает релизный конвейер, извлекая его из git-тега.**

1. **Версия объявлена в одном файле.** В `Directory.Build.props` задается `VersionPrefix`, из него выводятся `AssemblyVersion`, `FileVersion` и `InformationalVersion`. Отдельные свойства версии руками не заполняются.

   ```xml
   <PropertyGroup>
     <Product>TimeTracker</Product>
     <Company>TimeTracker</Company>
     <VersionPrefix>0.1.0</VersionPrefix>
   </PropertyGroup>
   ```

2. **Номер не вводится вручную.** Человек создает тег вида `v1.2.3`. Конвейер извлекает из имени тега `1.2.3` и записывает это значение в `Directory.Build.props` **перед** сборкой. Дальше идут сборка, упаковка и публикация артефакта.
3. **Установщик и обновление — Velopack** (ADR-009): он же служит каналом автообновления, поэтому отдельный механизм проверки версий не вводится.
4. **Артефакт этого этапа — Windows.** Linux и macOS отложены и перечислены как последующие шаги; их специфика на принятую схему версионирования не влияет, потому что номер версии от платформы не зависит.
5. **Инициализация обновлений происходит до создания окна** (порядок старта по ADR-003): проверка обновлений встраивается в старт приложения, а не выполняется по действию пользователя.
6. **Обновление не касается данных.** Папка данных находится вне области установки, поэтому замена файлов приложения не затрагивает ни базу, ни настройки.

---

## Последствия

**Положительные:**

- номер версии существует **в одном месте** — в файле сборки; приложение, установщик и информация о версии получают одно и то же значение;
- тег и номер связаны механически: расхождение невозможно, потому что номер берется из тега;
- версия доступна коду обычным способом (метаданные сборки), поэтому экран настроек показывает ее без отдельного хранилища и без файла настроек;
- обновление затрагивает только файлы приложения: пользовательские данные лежат в папке данных и при обновлении не участвуют.

**Отрицательные и ограничения:**

- **релиз начинается с тега.** Без тега конвейер не запускается, поэтому «просто собрать релиз» из интерфейса нельзя;
- **номер в файле меняет конвейер, а не человек.** Локальная сборка видит номер, записанный в файле, а не имя последнего тега: при локальной проверке нужно помнить, какое значение сейчас записано;
- **поставляется только Windows.** Пользователи Linux и macOS установщик пока не получат, хотя приложение там работает;
- **понижение версии не поддерживается.** Автообновление ведет только вперед, откат возможен лишь установкой более новой сборки с исправлением;
- **подпись кода и нотаризация отсутствуют** (вне рамок этапа): система может предупредить пользователя при установке.

---

## Альтернативы

1. **Править номер версии вручную в файле сборки.** Отклонено: номер оказывается в двух местах — в теге и в файле — и может разойтись с тем, что реально поставлено пользователю; проверка такого расхождения потребовала бы отдельного шага.
2. **Задавать версию только параметром сборки, без записи в файл.** Отклонено: локальные сборки, инструменты и создание миграций остались бы без номера, а воспроизводимость зависела бы от того, помнит ли человек добавить параметр. Значение, записанное в файл, служит точкой отсчета при повторной сборке того же тега.
3. **Упаковать сразу три операционные системы.** Отклонено: для Linux и macOS нужны свои проверки установки и удаления, а приоритет проекта — Windows (ADR-009). Сначала закрывается один работающий канал поставки.
4. **Задавать версию в каждом проекте отдельно.** Отклонено: приложение одно, и один номер должен относиться ко всей сборке, иначе установщик и приложение смогут получить разные значения.
